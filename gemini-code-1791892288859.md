# DocPulse AI: Multi-Tenant Enterprise RAG Copilot

## 📖 Project Overview

DocPulse AI is an enterprise-grade Retrieval-Augmented Generation (RAG) system designed to securely ingest documents and provide context-aware conversational AI search capabilities. The system guarantees strict data isolation across multiple tenants (e.g., departments, clients, or organizations), ensuring users only receive AI-generated answers based on the documents they are authorized to access. 

This project goes beyond a basic "chat with your PDF" script by implementing asynchronous ingestion pipelines, vector similarity metadata filtering, conversational memory, and low-latency token streaming using Server-Sent Events (SSE).

---

## 🏗️ System Architecture & AI Data Flow

The system is decoupled into a static frontend, a stateless API backend, an AI inference provider, and a managed vector database.

### The AI Generation Flow
1. **Document Ingestion & Chunking:** Uploaded files (PDF, DOCX) are parsed using Apache Tika. The text is processed by a `TokenTextSplitter` into overlapping chunks (e.g., 500 tokens with a 50-token overlap) to retain contextual boundaries.
2. **Metadata Enrichment:** Every chunk is stamped with metadata attributes, prominently the `tenant_id` and `document_name`.
3. **Vector Embedding:** Text chunks are transformed into high-dimensional vectors via an embedding model and stored in a PostgreSQL database utilizing the HNSW (Hierarchical Navigable Small World) index for lightning-fast approximate nearest neighbor searches.
4. **Tenant-Isolated Retrieval (RAG):** When a user submits a prompt, the system constructs a `FilterExpression` (`tenant_id == current_user.tenant_id`). The database retrieves only the mathematically similar chunks belonging to that specific tenant.
5. **Guardrails & Generation:** A `RetrievalAugmentationAdvisor` evaluates the similarity scores. If the top results fall below a defined confidence threshold (e.g., `< 0.72`), the system intercepts the prompt and gracefully responds: *"The provided documentation does not contain this information,"* effectively eliminating hallucinations.

## 🚀 Technology Stack

The entire stack is designed to be production-ready while utilizing free-tier open-source infrastructure for zero-cost deployment.

### Backend Core
* **Java 21:** Leverages Virtual Threads for high-throughput, non-blocking I/O operations (crucial when waiting for LLM API responses and database vector operations).
* **Spring Boot 3.4.x:** The foundational API framework utilizing Spring Security and Spring WebFlux.
* **Spring WebFlux (SSE):** Provides Server-Sent Events to stream LLM responses in real-time to the client.

### AI Integration Layer (Spring AI)
* **Spring AI (v1.1.0 BOM):** The orchestration framework that standardizes interactions with Large Language Models and vector databases.
* **LLM Provider:** Groq Cloud Free Tier running open-source models (e.g., **LLaMA 3.1** or **Mistral**) for ultra-fast inference, or optionally local execution via Ollama.
* **Embedding Model:** HuggingFace `bge-small-en-v1.5` or `nomic-embed-text`.
* **Document Parser:** Apache Tika for extracting raw text from binary document formats.

### Database & Persistence
* **PostgreSQL 16:** Relational database core.
* **pgvector Extension:** Native Postgres extension for vector storage and HNSW indexing.

### Frontend UI
* **React + Vite:** Lightweight Single Page Application.
* **Tailwind CSS:** For building a clean, modern, glassmorphic chat interface.

## 📋 Prerequisites & Tools Required

To build and deploy this project, you will need the following tools configured:

* **Development Environment:** JDK 21+, Maven 3.9+, Node.js 20+.
* **Containerization:** Docker Desktop (required to run `pgvector` locally).
* **Cloud Accounts (Free Tiers):**
  * **GitHub:** For version control and CI/CD pipelines.
  * **Groq Cloud:** For generating free API keys to access LLaMA 3 models.
  * **Supabase or Neon:** For a managed PostgreSQL database with `pgvector` pre-installed.
  * **Render.com:** For hosting the Spring Boot Docker container.
  * **Vercel:** For hosting the frontend React application.

## 🗓️ Development & Deployment Roadmap (4-Week Timeline)

### Week 1: Infrastructure, Vector Store & Ingestion Pipeline
* **Goal:** Set up persistent storage, local Docker environment, and a working multi-tenant chunking API.
* **Tasks:**
  1. Provision a local Docker Postgres instance with `pgvector`.
  2. Initialize the Spring Boot project with the `spring-ai-bom` and `spring-ai-starter-vector-store-pgvector` dependencies.
  3. Design the database schema and initialize the HNSW index.
  4. Implement `DocumentParserService` using Apache Tika to parse PDFs.
  5. Build the text splitting pipeline and apply `tenant_id` metadata to chunks.
  6. Expose the `POST /api/v1/documents/upload` REST endpoint.

### Week 2: Retrieval Engine, Metadata Filtering & Guardrails
* **Goal:** Implement secure similarity search, tenant isolation, and hallucination fallbacks.
* **Tasks:**
  1. Integrate the Spring AI `ChatClient` and configure it to point to the Groq API.
  2. Implement Spring AI `FilterExpressionBuilder` to enforce tenant ID matching on all vector queries.
  3. Create a `RetrievalAugmentationAdvisor` chain to enforce similarity thresholds.
  4. Implement `MessageWindowChatMemory` to retain multi-turn conversational context.
  5. Write integration tests to verify cross-tenant data isolation (Tenant A cannot see Tenant B's documents).

### Week 3: Streaming API & Frontend UI
* **Goal:** Build the real-time SSE streaming layer and a lightweight React frontend.
* **Tasks:**
  1. Implement `GET /api/v1/chat/stream` returning `Flux<ServerSentEvent<String>>` using Spring WebFlux.
  2. Scaffold a React UI using Vite and Tailwind CSS.
  3. Build the chat interface that consumes the SSE stream and renders tokens dynamically.
  4. Build the drag-and-drop document upload interface allowing the user to specify their tenant scope.
  5. Run an end-to-end test connecting the React app to the local Spring Boot backend.

### Week 4: Multi-Stage Dockerization, CI/CD & Cloud Deployment
* **Goal:** Achieve zero-cost deployment to public URLs with automated build pipelines.
* **Tasks:**
  1. Write a Multi-Stage `Dockerfile` utilizing an Eclipse Temurin 21 Alpine JRE to minimize image size.
  2. Provision a remote Supabase Postgres database and execute the `pgvector` extension setup.
  3. Create a `.github/workflows/build.yml` file for GitHub Actions to compile and test code on every push.
  4. Deploy the backend to Render.com Web Services and pass cloud environment variables (`GROQ_API_KEY`, `SPRING_DATASOURCE_URL`).
  5. Deploy the React frontend to Vercel and configure CORS on the backend to accept requests from the Vercel domain.

## 🛠️ Progress Monitoring & Git Strategy

To maintain a professional engineering workflow throughout the project lifecycle:

1. **GitHub Projects (Kanban):** Map the weekly tasks into a Kanban board (`Todo`, `In Progress`, `Review`, `Done`).
2. **Feature Branching:** Never commit directly to `main`. Create branches like `feature/document-ingestion`, `feature/sse-streaming`, or `fix/cors-issues`.
3. **Conventional Commits:** Write clean, descriptive commit messages (e.g., `feat: implement async PDF chunking with Apache Tika`, `docs: update deployment architecture in README`).
4. **Pull Requests:** Merge feature branches into `main` via PRs to maintain a clean, traceable Git history.
